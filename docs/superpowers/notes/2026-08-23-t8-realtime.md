# T8 — Inbox em tempo real via Supabase Realtime (evidências da prova manual)

Fecha a Task 8 do Plano C (ADR-0005). Setup da prova: web `next dev` local (:3000) + API da branch local (:3001) lendo o **Supabase vivo** (Redis de teste isolado, idx 1 — zero interferência nas filas do deploy), browser headless gstack logado com o usuário piloto real (JWT Supabase de verdade). O tráfego inbound continuou entrando pelo deploy do EasyPanel — a prova cobre o caminho completo de produção do dado: webhook → pipeline → Supabase → Realtime → browser.

## O que foi implementado

- `apps/web/lib/realtime.ts` — hook `useInboxRealtime`: um canal por página assinando `postgres_changes` INSERT/UPDATE de `messages`/`conversations` (RLS da T2 filtra por company no Postgres). **Evento é sinal, não fonte de dados**: dispara refetch debounced (300ms) dos DTOs validados da API — mapear linha crua→DTO no front duplicaria a tradução que vive na API (§4). Todo `SUBSCRIBED` (primeiro e resubscribes) dispara refetch de segurança.
- Componentes do inbox: poll de 15s removido; `refreshVersion` propagado pela página; dedupe por id no append otimista; composer passa a usar o `messageId` real do 202 como id do item otimista.
- **CORS (metade "código" da T9 adiantada)**: `@fastify/cors` gated por env `WEB_ORIGIN` (ausente = comportamento atual); hook de auth libera `OPTIONS` (preflight é anônimo por spec). Testes em `apps/api/test/cors.test.ts` (4 casos). Limitação documentada no app.ts: 401 do hook de auth sai sem headers CORS.
- Fix de flake pré-existente: `send-flow.test.ts` "corrida do eco no CAS final" sem timeout explícito (default 5s) flakeava por latência de rede até o droplet — agora `20000` como os vizinhos (provado idêntico com e sem as mudanças da T8).

## Latência — número honesto e o que falta

Medição single-clock (PC): `POST /messages` → bolha no DOM = **4,17s** na topologia dev. O gargalo é a topologia, não o design: API **local** falando com o Supabase pela internet residencial (rota de envio + refetch = múltiplos RTTs de ~200–400ms cada). Em produção (T9/T10: browser → API no EasyPanel → Supabase, datacenter-a-datacenter) esses saltos caem uma ordem de grandeza. **O critério "<2s" do Plano C será re-medido no E2E da T10 na topologia de produção** — se ainda estourar lá, otimizar então (reduzir debounce; mapear INSERT direto para a conversa aberta como fast-path).
